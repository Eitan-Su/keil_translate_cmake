Project Overview

将 Keil 工程转换为可在 VS Code 中编译、烧录与调试的 CMake 工程

当前程序的核心职责，是读取 .uvprojx 工程文件，提取目标芯片、源文件、头文件目录、宏定义、编译参数、链接脚本与 RTE 组件信息，然后生成新的 CMakeLists.txt、工具链文件、构建脚本以及 VS Code 配置。生成结果既保留了 Keil 工程的主要构建信息，也补上了 GCC 场景所需的启动文件、链接脚本、调试器配置与产物导出规则。

PySide6 图形界面 命令行入口 ArmClang GNU Arm Embedded GCC OpenOCD J-Link Cortex-Debug RTE 组件解析
当前实现的重点目标，是把 Keil 项目尽量转换为可直接使用的 CMake 工程；其中 STM32F103 与 AT32F415 已经补齐了较完整的自动处理分支，因此在 VS Code 中使用任务命令进行编译与烧录的成功率较高。其他系列通常仍可完成基础转换，但常需要补写芯片特定规则。

处理顺序

从输入工程文件到生成 VS Code 工程，内部处理大致分为八步。

1
定位 Keil MDK
优先检查显式参数，其次读取环境变量，再扫描常见安装目录与盘符候选目录；最终以 TOOLS.INI 是否存在作为判定依据。
2
解析 .uvprojx 基本信息
读取目标名、输出目录、输出产物名、目标芯片型号、厂商、CPU 描述串与存储器区间。
3
收集源文件与头文件目录
遍历 <Group> 与 <File> 节点，将源文件、头文件目录与显式包含目录统一转换为规范绝对目录，再在写文件阶段转回相对表示。
4
翻译编译参数
将 Keil 中的优化等级、C 标准、C++ 标准、FPU、大小端、R/O PI、LTO 等选项转换为 ArmClang 或 GCC 可理解的标志集合。
5
解析链接设置与 RTE 组件
提取 scatter 文件、Misc 链接参数，并通过 RTE 组件信息查找 PDSC 文件，把组件自带源文件与目录一并纳入工程。
6
为 GCC 做额外推断
尝试把 MDK 目录下的启动文件切换到 GCC 版本；如仅存在 ARMASM 启动文件，则自动生成 GNU 汇编版本；如缺失 .ld 文件，则依据 IROM 与 IRAM 自动写出回退链接脚本。
7
生成构建与调试文件
写入 CMakeLists.txt、工具链文件、构建脚本、VS Code 设置、任务列表、启动配置与 J-Link 命令脚本。
8
在 VS Code 中执行
生成的任务会自动调用 CMake 进行配置与编译；GCC 模式下还会额外产生 ELF、HEX、BIN 与 map 文件，并提供 OpenOCD 或 J-Link 烧录入口。

GUI 与 CLI

图形界面负责收集参数

图形界面包含九类主要输入项：工程文件、Keil MDK 目录、输出目录、编译器、宿主系统、Generator、硬件探针、调试后端与构建目录。勾选“生成 VS Code 配置”后，会额外输出 .vscode 目录。

编译器
支持 armclang 与 gcc。二者的默认构建目录分别为 build 与 build-gcc。
宿主系统
支持 Windows、Linux、macOS。调试命令名称与脚本后缀会随宿主系统变化。
探针与调试后端
探针支持 ST-Link、J-Link、DAPLink、Nu-Link、ULINK；后端支持 OpenOCD、J-Link GDB Server、PyOCD、Keil MDK 与关闭调试配置。

命令行便于批量转换

命令行入口覆盖了与图形界面相近的参数集合，适合脚本化批量转换与快速验证。

python keil_to_cmake.py project.uvprojx ^
  --compiler gcc ^
  --host-os windows ^
  --generator Ninja ^
  --debug-probe stlink ^
  --debug-backend openocd ^
  --build-dir build-gcc ^
  --export-vsc-settings ^
  --destination D:\output\demo
图形界面与命令行最终都会调用 KeilProjectToCMake.generate_cmake()，因此行为保持一致，差异只在于参数输入方式。

构建脚本的作用

程序还会生成 do_build.bat 或 do_build.sh。ArmClang 模式下，Windows 脚本会尝试从 KEIL_MDK_ROOT、用户默认 Keil 目录或常见本地目录自动补全 ARMCLANG_PATH。GCC 模式下则主要负责执行 CMake 配置与编译。

VS Code 输出

勾选 VS Code 输出后，生成器会写入四类 JSON 文件，并在 GCC 模式下补充 J-Link 命令脚本。

文件 作用 要点
settings.json 配置 CMake 生成器与构建目录 同步 compile_commands.json，ArmClang 模式可写入 cmake.configureEnvironment
tasks.json 定义配置、编译、重建、烧录与 GDB Server 任务 GCC 模式的 Build 任务会指向产物目标，保证生成 .hex 与 .bin
launch.json 供 Cortex-Debug 扩展使用 可生成 OpenOCD、J-Link、PyOCD 启动项，ArmClang 模式下也可保留 Keil 任务
c_cpp_properties.json 补全 IntelliSense 包含工程目录、解析得到的头文件目录与 compile_commands.json

支持范围

当前实现并非任意 Keil 工程均可零修改转换，而是具备通用解析能力，并对若干常见 Cortex-M 系列做了增强。支持情况可概括为下表。

目标系列 解析阶段 GCC 编译阶段 VS Code 烧录阶段 当前判断
STM32F103 完整 完整，含启动文件转换、core_cm3.c 修补、F1 宏推断、回退 .ld 完整，OpenOCD 默认目标指向 stm32f1x.cfg 可直接使用
AT32F415 完整 完整，支持 MDK 启动文件切换到 GCC 版本并推断 AT32F415xB_FLASH.ld 完整，OpenOCD 默认目标指向 artery/at32f4x.cfg，J-Link 启动项可生成 可直接使用
其他 STM32 系列 大多可解析 视启动文件、链接脚本与宏约定而定 OpenOCD 目标脚本仅覆盖 F0、F1、F3、F4、G0 常需适配
其他 AT32 系列 大多可解析 若目录结构与 F415 相近，编译机会较高 OpenOCD 默认仅写死到 at32f4x.cfg 常需适配
其他厂商 Cortex-M 基础解析通常可用 需补写宏、启动文件、链接脚本或工具链细节 探针目标脚本与器件名通常需手工补充 需要较多适配

STM32F103 可直接使用的原因

当前代码对 STM32F103 的兼容处理最完整，尤其照顾了 Keil 老工程中常见的标准库目录结构与 ARMASM 启动文件格式。这一分支并非只做到能解析工程，而是针对 GCC 构建与 VS Code 调试阶段补了多个细节。

1
自动推断 F1 标准库宏：会从启动文件名中提取 STM32F10X_MD 等宏；若启动文件无法直接给出，程序还会依据芯片名与 Flash 容量推断低密度、中密度、高密度或互联型宏。
2
ARMASM 启动文件自动改写为 GNU 汇编：对于仅包含 startup_stm32f10x_*.s 的 Keil 项目，可从向量表解析中断入口并生成新的 startup_..._gcc.S。
3
修补 core_cm3.c 的 GCC 约束问题：检测到旧版 CMSIS 的 strex/strexb/strexh 内联汇编写法后，会生成修补后的 core_cm3_gcc.c，避免 GCC 编译报错。
4
缺失 .ld 时自动生成回退脚本：根据 IROM 与 IRAM 的地址和长度写出新的 generated_linker.ld，因此老式 Keil 工程即使只有 scatter 信息，也能继续生成 GCC 工程。
5
OpenOCD 默认目标脚本已经就位：芯片名前缀匹配到 STM32F1 后，会自动采用 target/stm32f1x.cfg。

AT32F415 可直接使用的原因

AT32F415 分支的优势在于，很多工程本身就同时带有 GCC 启动文件与 .ld 文件。当前程序又针对 ArteryTek 系列补了默认 OpenOCD 目标脚本，因此整体转换难度明显低于只有 MDK 启动文件的老工程。

当前实现已经覆盖的关键点

处理点 当前行为 意义
启动文件目录切换 若检测到源文件位置包含 /startup/mdk/，会优先尝试切换到 /startup/gcc/ 避免继续使用仅适用于 ARMASM 的启动文件
链接脚本推断 会优先在启动文件同级的 linker 目录内搜索 .ld，并依据芯片名、内存码与文件名权重选出最佳候选 可自动找到类似 AT32F415xB_FLASH.ld 的文件
OpenOCD 默认目标脚本 厂商为 ArteryTek 或设备名前缀为 AT32 时，默认使用 target/artery/at32f4x.cfg 使 ST-Link 场景能自动生成可用任务
本地 openocd 目录匹配 若工程目录或上级目录存在 openocd 文件夹，会对其中 .cfg 文件做器件名与探针名匹配 优先使用工程自带的板级配置，而不是通用目标脚本
J-Link 启动配置 会额外生成 J-Link 的烧录脚本与 Cortex-Debug 启动项 便于在 ST-Link 之外切换到 J-Link 
AT32F415 工程中常见的生成特征

startup/gcc/startup_at32f415.s
startup/gcc/linker/AT32F415xB_FLASH.ld
openocd/at32f415_stlink.cfg

因此，AT32F415 系列之所以能在 VS Code 中较顺畅地执行任务命令，关键不在于程序识别了芯片名，而在于 GCC 启动文件、.ld 文件、OpenOCD 脚本、调试器参数四项都已有相应的自动处理。

常见适配顺序

1
先确认生成后的 CMakeLists.txt 是否引用了正确的启动文件与链接脚本。
2
再确认 target_compile_definitions() 中的器件宏是否满足厂商库的头文件判断。
3
随后检查 launch.json 与 tasks.json 中的探针脚本、GDB Server 类型与器件名。
4
最后处理少量编译器差异，例如内联汇编、库函数、链接符号或厂商专用启动代码。

    if clean_device.startswith("GD32F30"):
        return "target/stm32f1x.cfg"

边界与限制

当前实现已经比只生成一个 CMakeLists.txt 更进一步，但仍有几个边界需要在阅读和使用时保持清楚。

程序目前主要依据 Cortex-M 目录结构、器件名前缀与少量厂商特征进行判断，并没有内建一套完整的“所有厂商、所有系列”器件数据库。因此系列名称只要偏离当前规则，就可能出现宏名错误、链接脚本误选或探针脚本错误。
类别 当前状态 可能影响
OpenOCD 默认目标脚本 仅显式覆盖 STM32F0、F1、F3、F4、G0 与 AT32F4 新系列会回退到不合适的目标脚本
设备宏推断 对 STM32F1 做了特别处理，对其他系列较保守 标准库或 HAL 头文件可能缺少关键宏
J-Link 烧录脚本 BIN 下载地址固定写为 0x08000000 非标准 Flash 基址设备无法直接使用 BIN 任务
回退链接脚本 依据 IROM 与 IRAM 信息生成通用模板 复杂存储器布局、外部 RAM、特殊段属性场景仍需手工调整
启动文件转换 针对常见 ARMASM 向量表写法 厂商自定义语法或复杂预处理时可能需要单独处理
